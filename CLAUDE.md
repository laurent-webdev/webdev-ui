# Nouveau framework CSS/JS (nom à définir)

La v2 de webdev-ui : une refonte totale, en mieux, plus native, avec une meilleure architecture (précisé par Laurent, 2026-10-23). L'ancienne version est dans `/home/laurent/dev/webdev-ui_archive` : lecture seule, on ne touche jamais à son code, et aucune compatibilité avec elle n'est recherchée.

## Objectif

Un framework **ultra léger, simple, personnalisable, facile à utiliser**. En cas de doute : faire plus simple, ou ne pas faire.

## Référence : Bootstrap 6

**On s'inspire de Bootstrap 6 (v6.0.0-alpha.1), sans le copier** (précisé par Laurent, 2026-10-23) : ses classes et ses composants basés sur le HTML natif sont un bon modèle. En cas de question (noms de classes, variantes, valeurs), regarder comment Bootstrap 6 fait, puis garder ce qui est le plus simple. On s'en écarte librement quand c'est plus simple ou plus juste.

**Exception : les noms des variables CSS sont ceux de Laurent, pas ceux de Bootstrap** (précisé par Laurent, 2026-10-22). Ils doivent se comprendre sans doc : nom complet de la propriété CSS qu'ils règlent, pas de jargon (`--focus-outline-width` qui règle `outline-width`, pas `--focus-ring-width`). Bootstrap sert pour les valeurs, pas pour les noms de variables.

Ce que fait Bootstrap 6 (relevé dans `dist/css/bootstrap.css`, octobre 2026) :

- **Layers** : `@layer colors, config, root, reboot, layout, content, forms, components, custom, helpers, utilities;`. Couleurs avec `light-dark()`, `color-scheme: light dark`, thème forcé par `[data-bs-theme]`. Media queries en syntaxe d'intervalle (`@media (width >= 768px)`), container queries.
- **Variables** : préfixe `--bs-` (nous : aucun préfixe). Locales `--bs-<composant>-<propriété>` (`--bs-btn-padding-y`).
- **Couleurs** : palettes oklch (`--bs-blue-500: oklch(60% 0.24 240deg)`), paliers 025 à 975 obtenus par `color-mix` avec blanc (025-400) ou noir (600-975). Familles sémantiques : primary, accent, success, danger, warning, info, inverse, secondary. Chacune a `-base`, `-fg`, `-fg-emphasis`, `-bg`, `-bg-subtle`, `-bg-muted`, `-border`, `-focus-ring`, `-contrast` (page « Theme » lue le 2026-10-26) : une map Sass `$theme-colors` qui choisit un palier par rôle, dans un `light-dark()` (primary : base et bg 500, fg 600 / 400, fg-emphasis 800 / 200, bg-subtle 100 / 900, bg-muted 200 / 800, border 300 / 600, focus-ring = 500 mélangé à 50 % au fond de page, 75 % en sombre) ; `contrast` écrit à la main (blanc, `gray-900` pour warning et info), pas calculé ; paires conseillées : contrast sur bg, fg sur subtle, fg-emphasis sur muted. Changer une couleur demande de recompiler le Sass (la doc : changer seulement base et bg laisse les autres tokens à l'ancienne couleur). Surfaces `--bs-bg-body`, `--bs-bg-1` à `-4` ; textes `--bs-fg-body`, `--bs-fg-1` à `-4`.
- **Système de thème** : une classe `.theme-<couleur>` pose des tokens génériques (`--bs-theme-bg`, `-fg`, `-fg-emphasis`, `-contrast`, `-bg-subtle`, `-bg-muted`, `-border`, `-focus-ring`) ; les composants ne lisent que ces tokens. Ex. : `<button class="btn btn-subtle theme-success">`.
- **Bouton** : `.btn` + variante `.btn-solid` / `.btn-outline` / `.btn-subtle` / `.btn-text` (+ `.btn-link`, `.btn-icon`), tailles `.btn-sm` / `.btn-lg`. Survol : `oklch(from <couleur> calc(l * .95) calc(c * 1.1) h)`, clic : `calc(l * .9) calc(c * 1.15)`.
- **Espacements** : `--bs-spacer-0` à `-12`, fixes : 0, 0.25, 0.375, 0.5, 0.75, 1, 1.25, 1.5, 1.75, 2, 2.25, 2.5, 3rem. Utilitaires `m-*`, `p-*` (côtés `t b s e x y`), `gap-*`, `row-gap-*`, `column-gap-*`, `space-x-*`, `space-y-*`.
- **Rayons** : `--bs-radius-0` à `-9` (0 à 1rem) + `--bs-radius-pill`. Bordure `--bs-border-width: 1px`.
- **Typo** : `--bs-font-size-xs` à `-6xl`, fluides (`clamp()`) à partir de `lg` ; graisses `light` 300 à `bold` 700 ; titres h1 = 3xl … h6 = sm.
- **Breakpoints** : sm 576, md 768, lg 1024, xl 1280, 2xl 1536 px. Classes responsive préfixées : `md:d-flex` (comme nous).
- **Utilitaires** : noms abrégés gardés (`d-flex`, `text-center`, `fw-bold`, `fs-lg`, `w-100`) ; couleurs de texte `fg-*` ; `bg-*` ne pose que le fond.
- **Accessibilité** : `--bs-focus-ring-width: 3px`, `--bs-focus-ring-offset: 1px`, `button:focus:not(:focus-visible) { outline: 0; }`.
- **Non vérifié** (docs illisibles par l'outil) : liste complète des composants, JS (`<dialog>`, `popover`, anchor positioning), règles exactes de `.theme-*` (en partie lues le 2026-10-26 : `.theme-primary` pose `--bs-theme-bg: var(--bs-primary-bg)`… ; `.theme-reset` remet les `--bs-theme-*` à `initial`).

## Règles absolues

- **0 dépendance à l'exécution.** Le CSS et le JS livrés ne dépendent d'aucune librairie. Seuls outils de build autorisés : `sass` et `typescript`.
- **Personnalisation = variables CSS uniquement.** Aucune valeur de configuration en JS ou en SCSS. Changer une valeur ne doit jamais demander de rebuild.
    - **Règle indiscutable (Laurent)** : toutes les valeurs sont des variables CSS. Pas de map Sass. Rester simple, comme `webdev-ui_archive/src/scss/abstracts/variables.scss`.
    - Les couleurs dérivées (`--color-*-contrast`, `-state`, `-subtle`, `-emphasis`, `-emphasis-strong`, `-border`, `-subtle-border`) sont écrites par des mixins de `tools/_mixins.scss` (`contrast-colors`, `state-colors`, `subtle-colors`, `emphasis-colors`, `emphasis-strong-colors`, `border-colors`, demande de Laurent), appelés dans le `:root` de `_colors.scss` avec la liste `$colors`. Le CSS produit est le même qu'écrit à la main : une nouvelle couleur s'ajoute dans `--color-*` et dans `$colors`.
    - Seule exception : les breakpoints (`var()` ne fonctionne pas dans `@media`), définis en variables SCSS.
- **Couleurs en oklch** (choix de Laurent, 2026-10-21, après des essais en hexa + Sass puis en HSL) : dérivées calculées dans le navigateur depuis les `--color-*` (`oklch(from)`, `color(from)`), donc un site change une couleur sans rebuild. **Pas de couleurs de repli** (décision de Laurent, 2026-10-21) : `light-dark()` (Baseline mai 2024) et `color(from)` (Baseline sept. 2024) seront « largement disponibles » (30 mois) vers novembre 2026 et mars 2027, avant la sortie du framework.
- **CSS d'abord, JS en dernier recours.** Avant d'écrire du JS, vérifier si c'est faisable en HTML/CSS natif (`<details>`, `<dialog>`, `popover`, `:has()`, `:checked`, `:focus-within`…).
- **HTML minimal.** Le moins de classes et de balises d'enveloppe possible.
- **Le plus natif possible.** Utiliser l'élément HTML qui fait déjà le travail (`<button>`, `<dialog>`, `<details>`, `<nav>`…) plutôt que de le recréer.
- **Accessibilité** : tous les attributs `aria-*` indispensables sont présents dans chaque exemple. Pas d'`aria-*` redondant avec le natif (ex. pas de `role="button"` sur un `<button>`). Navigation clavier et focus visible obligatoires.
    - **Les recommandations de MDN et du W3C passent en premier** (Laurent, 2026-10-25 : « on suit toujours les recommandations en premier de MDN ou W3C pour l'accessibilité ») : quand elles conseillent un attribut en plus pour la compatibilité, on le met, même s'il double un rôle (`role="status" aria-live="polite"`, MDN : « To maximize compatibility, add a redundant `aria-live="polite"` ») ; quand elles le déconseillent, on ne le met pas (`role="alert"` sans `aria-live` : VoiceOver iOS lirait deux fois).
- **Validation W3C : 0 erreur, 0 warning** sur le HTML (documentation et exemples compris).
- **Rien d'inutile.** Ne pas reprendre de webdev-ui les fonctionnalités complexes ou rarement utiles.
- **Seulement ce qui sert au quotidien.** Pas de classe « au cas où » (ex. pas de `border-top-left-radius-*`). Un besoin rare se règle en CSS dans le site ou en surchargeant une variable. Une classe est ajoutée le jour où elle devient vraiment utile.
- **Facile à étendre.** Les mixins et boucles SCSS permettent d'ajouter une valeur ou une classe en une ligne, sans toucher au reste.
- **Point de départ : les classes de l'archive**, triées une par une (garder, simplifier ou supprimer), puis réécrites en mieux, jamais copiées.
- **Variantes responsive (`md:`…) seulement pour la mise en page** : display, flex, grid, espacements, largeur et hauteur, proportions (`aspect-ratio`), position (`position-*` seulement), alignement du texte. Pas pour les couleurs, l'opacité, les bordures, les ombres, etc.

## Exigence qualité

- **Le framework ne doit jamais faire perdre de points.** Lighthouse (performance, accessibilité, bonnes pratiques, SEO) et validateur W3C : si une note baisse, la cause doit venir du site, jamais du framework.
- **Chaque composant a sa page de démo**, qui doit obtenir 100 dans les 4 catégories Lighthouse et 0 erreur / 0 warning au validateur W3C HTML.
- **Toujours les meilleures références** (Laurent, 2026-10-24) : les spécifications W3C / WHATWG (HTML, CSS), WCAG et l'ARIA Authoring Practices Guide pour l'accessibilité, MDN pour le bon usage et la compatibilité (statut Baseline) de chaque balise, attribut ou propriété, vérifiés avant de l'utiliser. Les frameworks (Bootstrap 6, Tailwind…) viennent après, pour comparer les solutions.
- **Composants robustes** : ils fonctionnent au clavier, avec un contenu long, en zoom 200 %, avec `prefers-reduced-motion`, et sans JS quand c'est possible.

## Nommage des classes

Inspiré de Bootstrap et Tailwind. Pas de préfixe sur les classes.

**Lisible avant tout.** Le nom complet de la propriété CSS est utilisé, sauf abréviations listées ci-dessous. Mieux vaut trop verbeux que pas assez.

| Cas | Format | Exemple |
|---|---|---|
| Utilitaire | `propriete-valeur` | `justify-content-center`, `text-align-center` |
| Composant | `composant` | `button`, `card` |
| Élément d'un composant | `composant-element` | `card-title`, `card-body` |
| Variante | `composant-variante` | `button-primary`, `button-outline` |
| Taille | `composant-taille` | `button-sm`, `button-lg` |
| Breakpoint | `breakpoint:classe` | `md:d-flex`, `lg:button-lg` |
| État | attribut natif ou ARIA | `disabled`, `aria-expanded`, `open` (pas de classe `is-*`) |

- **Tailles et breakpoints** : tailles `xs`, `sm`, `md`, `lg`, `xl` ; breakpoints `xs`, `sm`, `md`, `lg`, `xl`, `2xl` (`xs:` dès 360px : une classe sans préfixe vaut pour tous les écrans, petits compris). Une taille est un suffixe (`.btn-sm`, `.btn-lg`), un breakpoint est un préfixe (`md:d-flex`) : jamais `sm:` pour dire « petit » (décision de Laurent, 2026-10-22).
- **Toutes les tailles existent en classe** (Laurent, 2026-10-24), y compris celle qui vaut le défaut : `.btn-md` (mêmes valeurs que le `:root` du bouton), `.container-2xl` (même largeur que `.container`), comme `.col-12`, `.fs-md`, `.fw-normal`. Les valeurs sont écrites dans la classe, pas lues dans le `:root` : un site qui change le défaut garde la taille d'origine disponible.
- **Tailles fixes ou qui suivent le texte** (règle validée par Laurent, 2026-10-25) : un composant qui vit **dans le texte** (badge, spinner) suit le texte autour, en `em`, sans classes de taille (dans un titre ou un `btn-lg`, il grandit tout seul ; des tailles fixes le figeraient, des tailles en em seraient écrasées par son minimum de 12px). Un composant **posé dans la mise en page** (bouton, accordéon, plus tard les champs de formulaire) a des tailles fixes `-xs` à `-lg` sur l'échelle globale : hauteur prévisible, cible tactile minimale (WCAG 2.5.8 : `btn-xs` = 24px ; en em, un bouton dans un petit texte passerait dessous), même hauteur qu'un champ à côté. Comme Bootstrap 6 et Tailwind (boutons fixes, badges qui suivent le texte).
- **Abréviations autorisées** : uniquement les très connues — `d` (display), `m` / `p` (margin / padding) et leurs côtés `mt`, `mx`…, `w` / `h` (width / height), `fs` / `fw` / `fst` (font-size / font-weight / font-style, comme Bootstrap 6), `bg` (background-color, demandé par Laurent le 2026-10-24), `border` pour `border-width` et `border-color` (`border-2`, `border-primary`, `border-primary-emphasis`, demandé par Laurent le 2026-10-26, comme Bootstrap 6). Toute nouvelle abréviation doit être ajoutée ici.
- Tout en minuscules, mots séparés par `-`.
- En SCSS, le `:` des breakpoints s'échappe : `.md\:d-flex`. Les classes responsive sont générées par un mixin à paramètre `$breakpoint`, jamais écrites à la main.

## Variables CSS

- **Aucun préfixe** sur les variables ni sur les classes.
- **Nommage cohérent partout** (validé par Laurent, 2026-10-22 : simple, basique, modifiable ensuite) :
    - échelle globale = `--<propriété>-<valeur>` : `--font-size-lg`, `--font-weight-bold`, `--space-3` ;
    - réglage d'un élément ou composant = `--<élément>-<propriété>` : `--heading-font-weight`, `--btn-padding-block`, `--focus-outline-width`.
    - **Quand l'un, quand l'autre** (2026-10-25) : une valeur partagée par plusieurs classes ou composants est une échelle, une variable par taille dans `settings/` (`--border-radius-md` est lu par `.border-radius-md`, `--btn-border-radius` et le focus des liens) ; une valeur propre à un composant est une seule variable par propriété, lue une fois dans la forme commune, que les tailles réécrivent sur leur classe (`.btn-sm { --btn-padding-block: 0.25rem; }`, `.container-xs { --container-max-width: … }`, comme Bootstrap) : pas de `--btn-padding-block-sm` dans le `:root`.
- **Globales** (dans `:root`) : `--color-primary`, `--space-2`, `--border-radius-md`, `--font`…
    - couleurs dans `settings/_colors.scss` ; espacements dans `settings/_spacing.scss` ; le reste (`--border-width`, `--border-radius-*`…) dans `settings/_variables.scss` ; `--border-color` dans `settings/_colors.scss`.
    - **Espacements** : `--space-0` à `--space-12`, règle droite `--space-n = n × --space` (0.25rem), de 0 à 3rem (2026-10-23 : on s'inspire de Bootstrap sans copier son échelle irrégulière). Le changer redimensionne toute l'échelle. Sert aux utilitaires (margin, padding, gap). `auto` est géré par les utilitaires.
    - **Utilitaires d'espacement** (`utilities/_spacing.scss`, 2026-10-23) : `m`, `mx`, `my`, `mt`, `mb`, `ms`, `me` (+ `-auto`) et les mêmes en `p`, de 0 à 12, en propriétés logiques (`mt` = `margin-block-start`, `ms` = `margin-inline-start`). Écrits dans cet ordre (tous les côtés, puis un axe, puis un côté) pour que le plus précis gagne : `class="m-4 mt-0"`. Variantes `xs:` `sm:` `md:` `lg:` `xl:` `2xl:`. Écriture choisie par Laurent le 2026-10-23, un entre-deux après deux essais (mixin `responsive` avec `@content` + `using` : syntaxe trop dure à lire ; une boucle `@for` par propriété écrite dans le fichier : trop long) : un mixin `spacing-classes($breakpoint: '')` dans le fichier, qui appelle `mixins.space-classes('#{$breakpoint}mt', margin-block-start)` une ligne par classe, puis appelé sans préfixe et dans chacune des 6 `@media` (comme `layouts/flex.scss` de l'archive). Chaque futur fichier responsive (display, flex, gap…) suit la même forme et recopie ses 6 `@media`. Poids mesuré avec les 5 breakpoints : le CSS passe de ≈ 18,5 à ≈ 68 Ko minifié, de ≈ 3,1 à ≈ 8,1 Ko compressé (189 classes + 945 responsive) ; avec `xs`, la grille et le container (2026-10-24, estimation sans Sass compressé) : ≈ 67 → 78 Ko minifié, ≈ 8,6 → 9,8 Ko compressé ; avec `gap-*` (273 classes) : ≈ 90 Ko minifié, ≈ 11,1 Ko compressé.
    - **Utilitaires gap** (`utilities/_gap.scss`, 2026-10-24) : `gap-0` à `-12`, `row-gap-*` (entre les lignes, vertical), `column-gap-*` (entre les colonnes, horizontal), valeurs `--space-*`, noms complets des propriétés CSS (pas `gap-x` / `gap-y` de Tailwind). Écrits dans cet ordre pour que le plus précis gagne (`class="gap-2 row-gap-8"`). Variantes `xs:` à `2xl:`, même forme que `_spacing.scss` (mixin `gap-classes($breakpoint)`, qui appelle `mixins.space-classes`). MDN : `gap` ne s'applique qu'aux conteneurs grid, flex et multi-colonnes (sans effet sur un bloc normal), Baseline « Widely available ». Sur `.grid`, le layer `utilities` passe devant `--grid-gap` : `class="grid gap-3"`.
    - **Utilitaires display** (`utilities/_display.scss`, 2026-10-24) : `d-none`, `d-inline`, `d-inline-block`, `d-block`, `d-flex`, `d-inline-flex`, `d-grid` (la liste de l'archive, celle de Bootstrap sans les `d-table*`, `d-inline-grid`, `d-contents`, `d-flow-root`, rarement utiles), une ligne par classe dans le mixin `display-classes($breakpoint)` (comme l'archive), variantes `xs:` à `2xl:`. Mots-clés de `display`, pas des réglages : pas de variable CSS. `d-none` masque aussi pour les lecteurs d'écran (MDN) ; un masquage visuel seul : `.visually-hidden` (fait le 2026-10-25). `d-grid` = grille sans colonnes (empiler avec `gap`), et sert à réafficher une `.grid` masquée (`class="grid d-none lg:d-grid"`). L'attribut `hidden` gagne toujours sur `d-*` (`!important` du reset). Pas de `print:` pour l'instant. Poids avec display : ≈ 91 Ko minifié, ≈ 11,4 Ko compressé.
    - **Utilitaires flex** (`utilities/_flex.scss`, 2026-10-24) : `flex-direction-row` / `-column`, `flex-wrap-wrap` / `-nowrap`, `justify-content-start` / `-center` / `-end` / `-space-between` / `-space-around` / `-space-evenly`, `align-items-start` / `-center` / `-end` / `-baseline` / `-stretch`, `align-self-auto` / `-start` / `-center` / `-end` / `-baseline` / `-stretch` (`auto` revient à l'`align-items` du parent), `flex-grow-0` / `-1`, `flex-shrink-0` / `-1`. Noms `propriété-valeur` complets, selon la règle de nommage (Bootstrap 6 abrège : `flex-column`, `flex-wrap`, `justify-content-between`) ; validé par Laurent le 2026-10-24 : « verbeuse oui, mais explicite, et c'est ce que je veux ». Valeurs `start` / `end` et pas `flex-start` / `flex-end` comme Bootstrap 6 : le nom de la classe est la valeur CSS, elles suivent le sens d'écriture et marchent aussi en grid (MDN ; `start` / `end` en flex : Chrome 93, Firefox 45, Safari 15.4, mars 2022, Baseline largement disponible). Écartés : `row-reverse`, `column-reverse`, `wrap-reverse` et `order-*` (MDN : l'ordre affiché ne suit plus le DOM, WCAG 1.3.2), `align-content-*`, `flex-fill` (rarement utiles, à ajouter le jour où ; `space-around` / `-evenly` et `align-self-*` ajoutés à la demande de Laurent le 2026-10-24). Une ligne par classe dans le mixin `flex-classes($breakpoint)`, variantes `xs:` à `2xl:`. Poids avec flex : ≈ 99 Ko minifié, ≈ 12,3 Ko compressé.
    - **Utilitaires largeur et hauteur** (`utilities/_sizing.scss`, 2026-10-24, en essai) : `w-25` / `-33` / `-50` / `-66` / `-75` / `-100` / `-auto` / `-fit-content`, `min-w-0`, `h-100`, `min-h-100svh`. Abréviations `w` / `h` (autorisées), valeur CSS dans le nom (`fit-content`, comme `start` en flex). Largeurs en % du parent, pas en `vw` (le % suit le container, la carte ou la colonne ; `100vw` compte la barre de défilement verticale, une barre horizontale apparaît). Quarts et tiers (Bootstrap 6 : quarts seuls ; les tiers ajoutés par Laurent le 2026-10-24 : « parfois on aime avoir 1/3 et 2/3 ») ; nom = le pourcentage arrondi, comme l'archive (`w-33`, `w-66`, pas `w-1/3` de Tailwind qui demande d'échapper le `/`), valeur exacte `calc(100% / 3)`, `calc(100% * 2 / 3)`. `min-w-0` : un enfant flex ou grid a `min-width: auto` (il ne descend pas sous son mot le plus long), la solution reconnue au débordement. **Hauteurs : seulement les courantes** (Laurent, 2026-10-24 : il s'en sert rarement, sauf pour un bandeau) : `h-100` (remplir un parent qui a une hauteur) et `min-h-100svh` (pied de page en bas d'une page courte, bloc plein écran) ; `h-25` / `-50` / `-75`, `h-auto`, `h-fit-content`, `min-h-0` retirés, à ajouter le jour où ils servent ; une autre hauteur d'écran (bandeau à 50 %…) s'écrit dans le site, en `svh`. `svh` : MDN, `vh` = `lvh` sur téléphone (le bas est caché sous les barres du navigateur), `dvh` redimensionne le contenu pendant le défilement (« performance hit »), `svh` est « safer » ; Chrome 108, Firefox 101, Safari 15.4 (novembre 2022, Baseline largement disponible). `fit-content` : Firefox 94 en dernier (novembre 2021). Écartés aussi (rarement utiles) : largeurs fixes en rem (`w-1` à `w-12` de Bootstrap 6), `min-content` / `max-content`, `max-w-100` (le reset met déjà `max-inline-size: 100%` sur les médias), `min-w-100`, `vw-100`. Propriétés physiques `width` / `height`, comme le nom (l'écriture de droite à gauche ne change pas la largeur). Variantes `xs:` à `2xl:` pour toutes (Bootstrap 6 n'en a pas ; la largeur est dans la liste des variantes de mise en page), mixin `sizing-classes($breakpoint)`. Démo, exemple (pied de page), contre-exemples (`w-100 mx-4` déborde ; flex sans `min-w-0`) et limites (hauteur en % sans parent qui a une hauteur ; `svh` laisse un peu de place quand les barres se cachent ; autres hauteurs dans le site) dans la section « Largeur et hauteur » de la page de test, parent de démo `.demo-height` (8rem) dans `doc.css`.

## Thèmes clair et sombre

- **Par défaut** : le thème suit le réglage du système de l'utilisateur.
- **Forcer un thème** : attribut `data-theme="light"` ou `data-theme="dark"` sur `<html>`.
- **Natif** : `color-scheme` + fonction `light-dark()`. Chaque couleur est déclarée une seule fois, avec ses deux valeurs. Les éléments natifs (champs de formulaire, barres de défilement) s'adaptent tout seuls.

```css
:root { color-scheme: light dark; }
:root[data-theme="light"] { color-scheme: light; }
:root[data-theme="dark"] { color-scheme: dark; }

:root {
  --color-background: light-dark(#ffffff, oklch(0.18 0.005 245));
}
```

- Les composants n'utilisent que ces variables : ils n'ont **jamais** de règle spécifique au thème sombre.
- Le framework ne fournit pas de JS pour changer de thème. Le bouton de bascule et la mémorisation du choix sont gérés par le site. Exemple dans la doc : bouton `#theme-toggle` dans `base.html.twig`, script inline dans `<head>` (thème mémorisé posé avant le CSS, sans flash) et bascule dans `doc/assets/app.js` (`localStorage`, `aria-pressed`).
- Contrastes vérifiés dans les deux thèmes (accessibilité Lighthouse à 100 dans les deux).

## Organisation des fichiers

Architecture ITCSS (ordre de spécificité croissante), modules Sass (`@use` / `@forward`, jamais `@import`).

```
src/scss/
├── app.scss              un @use par dossier, rien d'autre
├── settings/
│   ├── _index.scss
│   ├── _layers.scss      ordre des @layer (premier CSS produit)
│   ├── _breakpoints.scss variables SCSS (seule config SCSS), pas de sortie CSS
│   ├── _colors.scss      couleurs oklch dans :root, avec light-dark(), et color-scheme
│   ├── _spacing.scss     échelle d'espacements --space-1 à --space-12
│   └── _variables.scss   autres variables CSS globales dans :root (rayons…)
├── tools/
│   ├── _index.scss       @forward des outils
│   └── _mixins.scss      boucle des espacements, couleurs dérivées, pas de sortie CSS
├── _reset.scss           remise à zéro, aucun style visuel (un seul fichier : pas de dossier)
├── base/                 styles des éléments natifs (texte, liens, focus-visible…)
├── layout/               container, grid (.grid, .col-*)
├── components/           un fichier par composant
└── utilities/            un fichier par famille d'utilitaires (spacing = m-*, p-*…)
src/ts/
├── bundle.ts             démarre tous les composants
└── components/           un fichier par composant qui a besoin de JS
```

- **Ordre** : settings → tools → reset → base → layout → components → utilities. Les utilitaires sont en dernier pour pouvoir surcharger les composants.
- **Pas de numéro dans les noms de dossiers** : l'ordre vient de `app.scss` et de `@layer`.
- **Un dossier seulement s'il contient plusieurs fichiers.** Un dossier a un `_index.scss` (convention Sass : `@use 'components'` charge `components/_index.scss`), qui liste ses fichiers par ordre alphabétique. Un fichier unique par nature (le reset) reste à la racine de `src/scss/`, sans dossier ni index.
- **Tout le CSS du framework est dans un `@layer`** : `@layer settings, reset, base, layout, components, utilities;`. Le CSS du site, écrit hors layer, gagne toujours sur le framework, sans bataille de spécificité.
- `tools/` et `settings/_breakpoints.scss` ne produisent pas de CSS : chaque fichier qui en a besoin les charge lui-même, avec un préfixe (`@use '../tools/mixins';` puis `@include mixins.contrast-colors(…)`). Pas de `as *` : l'IDE (JetBrains) ne retrouve pas la source et affiche « resolved only by name without use of explicit imports ».
- **Ajouter un composant** :
    1. créer `components/_nom.scss` (et `src/ts/components/nom.ts` si le JS est indispensable) ;
    2. ajouter `@use 'nom';` dans `components/_index.scss` ;
    3. créer sa page de documentation.

    Même principe pour un utilitaire ou une mise en page.
- **Nom de fichier = nom de la classe** : `_button.scss` contient `.button` et ses dérivés. Même nom pour le TS : `button.ts`.
- Fichiers en kebab-case, partials SCSS préfixés par `_`.
- **Contenu d'un fichier composant**, dans cet ordre : variables locales → styles de base → éléments → variantes → tailles → états.
- **Utilitaires** : générés par boucle SCSS sur une liste de clés, mais les valeurs viennent toujours des variables CSS (`.m-2 { margin: var(--space-2); }`).

## JavaScript (si indispensable)

- Écrit en TypeScript, livré en JavaScript vanilla (modules ES).
- Le JS change des attributs (`hidden`, `open`, `aria-*`), jamais de style inline.
- Initialisation via un attribut `data-*` au nom du composant (ex. `data-dropdown`).
- **Un composant = une classe** (Laurent, 2026-10-26 : « je préfère les classes, plus facile à comprendre et à maintenir » ; comme l'archive) : `export default class <Composant>` dans son fichier. Écouteurs en délégation : **méthodes statiques** (un seul jeu d'écouteurs pour la page, pas d'instance par élément), qui appellent `<Composant>.méthode()` et pas `this` (un écouteur reçoit `this` = `document`). Démarrée en bas de son fichier par `<Composant>.start()`, quand le bundle l'importe : le site n'écrit pas de JS. Le navigateur n'ajoute pas deux fois la même fonction avec la même capture : un second `start()` ne double rien, pas besoin de drapeau `initialized` comme l'archive. Pas de `destroy()` tant qu'il ne sert pas.
- **Sans état, rien à démarrer** (2026-10-25, `dialog.ts`) : un composant qui réagit à des événements écoute en délégation sur `document` (en capture pour les événements qui ne remontent pas : `cancel`, `close`, `command`) et vérifie son `data-*` : il marche pour le HTML ajouté plus tard, sans `MutationObserver`. `src/ts/bundle.ts` importe chaque composant (`import './components/dialog';`) . **Un seul fichier publié** : `dist/js/bundle.js` (+ `.min.js`) (2026-10-26, choix de Laurent : « un seul bundle » ; un composant fait quelques centaines d'octets, absent de la page il ne coûte que ses écouteurs, comme le CSS en un fichier ; un site qui chargerait `bundle.js` et `drawer.js` aurait deux copies de la classe, donc des écouteurs en double). Fichiers par composant à revoir si un composant devient lourd ; un site avec un bundler importe les sources de `src/ts/components/`. La doc charge `dist/js/bundle.js` dans `base.html.twig`, comme le CSS.
- **Événements pour le site** (Laurent, 2026-10-25 : « qqch qui émet des events pour faire des choses derrière pour les utilisateurs, c'est important pour certains composants ») : le JS d'un composant prévient le site de ce qu'il fait. **Natifs d'abord** : pas d'événement qui double un événement du navigateur. Dialogue : `cancel` (Échap, `requestClose()`) et `close` (MDN : HTMLDialogElement largement disponible), `command` (le bouton qui l'a ouvert ou fermé ; `CommandEvent`, Baseline 2025), `beforetoggle` (annulable à l'ouverture seulement) et `toggle`, hérités de HTMLElement (MDN : « may not be fired at dialog elements on all browsers ») ; accordéon : `toggle` sur `<details>`. Si le JS du framework anime la fermeture, il appelle `close()` à la fin : l'événement `close` natif arrive toujours, après l'animation. **Sinon** (état que le navigateur ne connaît pas : onglet choisi, notification) : `new CustomEvent()` sur l'élément du composant (celui qui a `data-<composant>`), `bubbles: true` (le site peut écouter sur `document`), les données dans `detail`, `cancelable: true` sur l'événement d'avant quand l'action peut être refusée. Nommage validé par Laurent le 2026-10-25 : `<composant>-<action>` en minuscules (`tab-change`), et `<composant>-before<action>` pour celui d'avant, annulable (`tab-beforechange`), sur le modèle de `beforetoggle` / `toggle` ; le nom du composant évite de croiser un événement natif (`change`). Chaque page de composant avec du JS liste ses événements.
